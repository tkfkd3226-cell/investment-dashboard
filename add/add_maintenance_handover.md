# add 영역 유지보수 및 거래 리포트 인수인계

> 적용 범위: `add/calc.html`, `add/css/*`, `add/js/calc.js`, `add/report/*` 및 **KODEX 레버리지 실현손익 반영 때문에 함께 수정되는 `data/portfolio.json`**
>
> 목적: 새로운 KODEX 레버리지 거래가 생길 때마다 리포트 구조·계산 기준·연동 파일을 다시 분석하지 않고, 아래 고정 절차와 산식으로 바로 갱신한다.

---

## 1. 작업 시작 시 읽기 순서

`add/` 영역 또는 KODEX 레버리지 거래 리포트를 수정할 때는 다음 순서로 확인한다.

```text
1. /main_dashboard_maintenance_handover.md
2. /add/add_maintenance_handover.md
3. 현재 ZIP의 실제 관련 소스
   - data/portfolio.json
   - add/calc.html
   - add/report/kodex-leverage-report.html
     (아직 canonical 전환 전이면 현재 존재하는 legacy dated report)
   - 필요 시 add/css/*, add/js/calc.js
4. 사용자가 이번 작업에 제공한 최신 증권사 원본 자료
```

현재 작업에서 사용자가 별도 요청을 주면 그 요청을 가장 우선한다.

과거 대화의 수치나 과거 ZIP을 최신값으로 추정하지 않는다. 최신 실제 파일과 이번에 제공된 증권사 원본을 사용한다.

### 1.1 add 영역 Responsive viewport 기준

`calc`와 거래 `report`의 기본 viewport는 메인 대시보드와 동일하게 아래 **3구간만 사용**한다.

```text
Desktop · 웹      ≥ 1101px
Tablet · 태블릿   761px ~ 1100px
Mobile · 모바일   ≤ 760px
```

- `720px`, `900px`, `700px`, `560px`, `419px`, `350px`, `319px`, 화면 높이 조건 등 add 전용/미관용 특수 viewport를 만들거나 유지하지 않는다.
- `max-width:1100px`처럼 Tablet+Mobile에 공통 적용하거나 `min-width:761px`처럼 Tablet+Desktop에 공통 적용하는 shared media는 위 경계값을 사용하는 한 허용한다.
- 화면이 좁아질 때 세부 글자 크기 보정이 필요하면 새 breakpoint를 추가하지 말고 `clamp()`, grid/flex, overflow 등 component 자체의 유동 규칙으로 우선 해결한다.
- 향후 사용자가 별도로 특수 viewport를 다시 요청하지 않는 한 `calc`와 `report`에는 이 3구간 외 viewport media를 추가하지 않는다.

## 2. 거래 리포트 canonical 파일명

거래 리포트의 canonical 파일명은 날짜 범위를 파일명에 넣지 않고 아래로 고정한다.

```text
add/report/kodex-leverage-report.html
```

기존처럼:

```text
20260608-20260812_report.html
20260608-20260820_report.html
...
```

형태로 매번 새 파일명을 만들지 않는다.

### 파일명 운영 규칙

- 거래기간의 시작일·최종일은 **리포트 본문에 표시**하고 파일명에는 넣지 않는다.
- 새 거래가 추가되어도 `kodex-leverage-report.html`을 계속 갱신한다.
- 사용자가 별도로 보관본 생성을 요청하지 않는 한 날짜가 붙은 병렬 report 파일을 만들지 않는다.
- 기존 날짜형 파일을 canonical 파일명으로 전환하는 작업에서는 기존 dated report를 제거하고 새 파일 하나만 남긴다.

`add/calc.html`의 거래 리포트 버튼도 항상 다음 고정 경로를 가리킨다.

```html
href="report/kodex-leverage-report.html"
```

파일명을 바꾸는 작업에서는 **report 파일만 변경하지 말고 `add/calc.html` 링크까지 반드시 함께 수정**한다.

아직 `kodex-leverage-report.html`이 없고 날짜형 report만 존재한다면, 다음 실제 거래 리포트 갱신 작업에서 canonical 이름으로 1회 전환한다. handover 파일 생성만을 위한 작업에서는 리포트 내용이나 파일명을 억지로 함께 변경하지 않는다.

## 3. 새로운 KODEX 레버리지 실현거래가 생겼을 때 기본 수정 범위

새로운 실현손익이 발생하면 기본적으로 아래 파일을 한 세트로 확인한다.

```text
data/portfolio.json
add/report/kodex-leverage-report.html
add/calc.html            # 링크/연동 확인. canonical 파일명 정착 후 보통 내용 변경 없음
add/add_maintenance_handover.md  # 운영 규칙이 새로 추가·변경된 경우에만
main_dashboard_maintenance_handover.md # 전역 반복 운영 규칙이 바뀐 경우에만
```

### 기본 원칙

> **리포트만 수정하지 않는다.**

새로운 실현손익은 메인 대시보드의 별도수익 계산에도 사용되므로 `data/portfolio.json`의 `separateProfit.trades`와 거래 리포트가 서로 일치해야 한다.

다음 파일은 단순히 새로운 실현거래가 생겼다는 이유만으로 수정하지 않는다.

```text
data/prices.json
data/performance_snapshots.json
data/pension_contributions.json
data/pension_trades.json
data/pension_cash_snapshots.json
메인 CSS/JS
```

실제 요청이 해당 파일의 책임까지 포함할 때만 수정한다.

## 4. 증권사 원본 자료별 역할

새 거래를 반영할 때 자료의 역할을 다음과 같이 고정한다.

### 4.1 매도실현손익 화면

날짜별 최종 확정값의 1차 기준이다.

다음 값을 읽는다.

```text
매도일
종목명
매도수량
평균매수가
평균매도가
손익금액
거래비용
순손익금액
수익률
누적 합계
```

특히 `data/portfolio.json`에 반영할 값은 **거래비용 차감 후 순손익금액**이다.

### 4.2 상세 매매보고서 / 매매내역

다음 용도로 사용한다.

```text
실제 매수일
실제 매도일
수량 연결
오버나이트 여부
본 포지션 / 단타 분류
타임라인 설명
```

### 4.3 자료가 서로 다르게 보일 때

- 날짜별 전체 손익·거래비용·순손익은 매도실현손익 화면을 우선한다.
- 매수일·보유기간·포지션 연결은 상세 매매보고서를 사용한다.
- 자료 간 불일치가 실제로 존재하면 임의로 숫자를 맞추지 말고 사용자에게 그 차이만 알린다.

## 5. `data/portfolio.json` 별도수익 반영 규칙

위치:

```text
data/portfolio.json
→ separateProfit
→ trades
```

각 항목은 다음 형식을 유지한다.

```json
{
  "date": "YYYY-MM-DD",
  "profit": 1090423
}
```

### 값의 의미

- `date` = **매도실현일**
- `profit` = 그 날짜의 **거래비용 차감 후 순손익**
- 손실이면 음수

### 날짜별 관리

- 원칙적으로 **매도일 1일당 1개 레코드**를 유지한다.
- 같은 날짜에 거래가 여러 번 있어도 증권사 매도실현손익 화면의 **그 날짜 전체 순손익**을 사용한다.
- 같은 날짜가 이미 존재하면 중복 레코드를 추가하지 말고 해당 날짜의 최종 확정값으로 갱신한다.
- 배열은 날짜 오름차순을 유지한다.

### 재투입 한도

```text
separateProfit.reinvestedLimit
```

은 사용자가 별도로 변경하라고 하지 않는 한 기존 값을 유지한다.

새 실현손익이 생겼다고 재투입 한도를 자동으로 늘리지 않는다.

## 6. 거래 리포트의 확정 계산 기준

### 6.1 날짜별 전체 실현손익

증권사 매도실현손익 화면의 날짜별 값을 그대로 사용한다.

기본 검산:

```text
손익금액 - 거래비용 = 순손익
```

전체 합계:

```text
Σ 날짜별 손익금액 = 총 손익금액
Σ 날짜별 거래비용 = 총 거래비용
Σ 날짜별 순손익 = 누적 실현 순손익
```

### 6.2 본 포지션 / 단타 분류

기본 분류는 다음과 같다.

```text
매수한 날을 넘겨 보유 후 매도
→ 본 포지션

같은 날 매수 후 같은 날 매도
→ 단타
```

한 매도일에 기존 보유분 청산과 당일 반복매매가 섞여 있으면 **혼합일**로 처리한다.

### 6.3 혼합일 단타 수량

현재 리포트의 기존 방법을 유지한다.

```text
혼합일 단타 매도수량
= 증권사 그날 전체 매도수량
- 확인 가능한 본 포지션 매도수량
```

### 6.4 혼합일 단타 손익금액

```text
혼합일 단타 손익금액
= 증권사 그날 전체 손익금액
- 확인 가능한 본 포지션 손익금액
```

### 6.5 혼합일 거래비용 배분

증권사 화면이 날짜별 총 거래비용만 제공하고 본 포지션/단타별 비용을 따로 제공하지 않는 경우, 기존 리포트와 동일하게 **추정 왕복 거래대금 비율**로 비용을 배분한다.

따라서:

- 본 포지션·단타 각각의 거래비용/순손익에는 추정값이 포함될 수 있다.
- 그러나 두 그룹 합계는 증권사 날짜별 정확값과 반드시 일치해야 한다.

검산:

```text
본 포지션 순손익 + 단타 순손익
= 전체 누적 실현 순손익
```

## 7. 신규 거래의 자금 출처는 추적하지 않는다

새 KODEX 레버리지 매매가 어떤 돈으로 이루어졌는지 매번 구분하지 않는다.

예:

```text
기존 보유 현금
급여 등 개인자금
신규 대출
기타 단기 자금
```

어느 자금으로 매매했는지 **사용자에게 다시 묻지 않는다.**

### 제외하는 변수

신규 매매와 관련하여 다음을 새로 계산하지 않는다.

```text
신규 차입원금
대출이자
대출 실행일
상환일
중도상환수수료
자금조달 비용
자금 출처별 ROI
```

### 투자손익 계산 원칙

매매 자금의 출처와 무관하게 투자 리포트에는 실제 거래에서 발생한:

```text
손익금액
거래비용
순손익
```

만 반영한다.

> **대출이자 등 금융비용은 본 거래 리포트의 투자손익에서 제외한다.**

## 8. 자금 흐름 / 차입금 섹션은 사용하지 않는다

현재 canonical 거래 리포트에서는 **자금 흐름 메뉴와 본문 섹션을 사용하지 않는다.**

과거 리포트에 있던 다음 계산·표시는 제거된 상태를 canonical로 본다.

```text
자금 흐름 메뉴
갚아야 할 총 차입원금
차입금 상환 후 현금
최종 순수 자기자금
자금 출처별 운용원금
대출이자·금융비용을 반영한 현금 계산
```

과거 차입·카드대금 관련 자금 흐름은 이미 종료된 과거 이력으로 취급하며, 신규 거래가 생길 때 다시 이어서 계산하지 않는다.

리포트에는 거래 자체를 설명하는 데 필요한 **매수원가·매도금액·손익·거래비용·순손익**만 남긴다. 예를 들어 대규모 추가매수 타임라인에는 실제 추가매수 금액은 표시할 수 있지만, 그 금액이 대출인지 자기자금인지 다시 분해하지 않는다.

향후 사용자가 명시적으로 자금 흐름 분석을 다시 요청하지 않는 한 `자금 흐름` 패널이나 `최종 순수 자기자금` KPI를 복원하지 않는다.

### 8.1 거래 흐름 Timeline 반응형 고정 규칙

거래 흐름 타임라인은 다음 표시 방식을 유지한다.

```text
웹 / 태블릿
- 날짜를 타임라인 좌측 별도 열에 표시
- 날짜는 줄바꿈하지 않고 한 줄 유지
- 기간 표기가 길어져도 날짜 열 폭을 확보

모바일 (≤760px)
- 좌측 날짜 텍스트는 숨김
- 타임라인 선과 점은 유지
- 같은 날짜를 각 네모 카드의 최상단에 표시
- 카드 내부 순서: 날짜 → 제목 → 핵심 거래내용 → 설명
```

날짜 형식은 기존 데이터의 의미를 유지하되 모바일 카드에서는 날짜가 누락되지 않아야 한다.

## 9. 리포트에서 새 거래 반영 시 반드시 함께 갱신할 부분

### Hero / 핵심 요약 KPI 고정 구성

거래 리포트 상단 정보구성은 임의로 다시 선정하지 않고 아래 구성을 유지한다.

```text
Hero 3개
1. 본 포지션 추정 순손익
2. 추정 단타 순손익
3. 누적 실현 순손익

핵심 요약 KPI 6개
1. 누적 실현 순손익
2. 총 손익금액
3. 총 거래비용
4. 본 포지션 추정 순손익
5. 단타 추정 순손익
6. 매도일 기준 승률
```

`매도일 기준 승률`은 **날짜별 순손익이 0원보다 큰 매도일 수 ÷ 전체 매도일 수 × 100**으로 계산하고 소수점 첫째 자리까지 표시한다. 0원인 날은 승리로 계산하지 않는다. 보조문구에는 `수익 N일 / 전체 N일`을 표시한다.

Hero는 Desktop에서 3개를 한 줄에 표시하고, Tablet/Mobile에서는 **2개 + 1개 전체폭(2+1)** 배치를 유지한다. 이때 전체폭이 되는 3번째 카드는 합계 성격의 `누적 실현 순손익`으로 고정한다. 카드 수나 문구가 바뀌었다는 이유로 별도 breakpoint나 신규 레이아웃을 만들지 않는다.

숫자 한두 군데만 수정하지 않는다. 아래 항목을 전체 검색해서 같은 기준으로 갱신한다.

```text
Hero 요약
KPI 카드
누적 실현 순손익
총 손익금액
총 거래비용
매도일 수
매도일 기준 승률
전체 매도수량
날짜별 실현손익 표
날짜별 누적 순손익
Chart data
본 포지션 요약
단타 요약
```

## 10. 증권사 원본 이미지 반영

리포트의 `증권사 실현손익 원본` 이미지가 base64로 내장되어 있다면 새 매도실현손익 화면을 제공받았을 때 최신 이미지로 교체한다.

함께 수정한다.

```text
섹션 업데이트 날짜/시각
<img alt="...">
필요한 caption 또는 설명
```

오래된 캡처와 최신 숫자가 한 리포트 안에 섞이지 않도록 한다.

## 11. 새 거래 반영 시 빠른 작업 절차

새 거래 자료가 들어오면 다음 순서로 처리한다.

```text
1. 증권사 매도실현손익에서 새 매도일의 확정 순손익 확인
2. 상세 매매보고서에서 매수일·수량·오버나이트 여부 확인
3. data/portfolio.json separateProfit.trades 갱신
4. report의 날짜별 표/합계 갱신
5. 본 포지션/단타 분류 및 혼합일 계산
6. chart / KPI / hero / 합계 / timeline 전부 갱신
7. Timeline 날짜가 웹/태블릿 한 줄, 모바일 카드 상단에 정상 표시되는지 확인
8. 최신 증권사 원본 이미지 교체
9. calc.html이 canonical report 경로를 가리키는지 확인
10. 아래 QA 검산 수행
```

자금 출처 질문이나 대출이자 분석은 위 절차에 넣지 않으며, 자금 흐름 패널이나 최종 자기자금 계산도 추가하지 않는다.

## 12. 필수 QA / 검산

새 거래 반영 후 최소한 다음은 확인한다.

```text
[ ] 새 매도일의 수량/평균매수/평균매도/손익/비용/순손익이 증권사 원본과 일치
[ ] 날짜별 손익금액 - 거래비용 = 날짜별 순손익
[ ] 전체 손익금액 - 전체 거래비용 = 전체 누적 실현 순손익
[ ] 날짜별 순손익 합계 = 전체 누적 실현 순손익
[ ] data/portfolio.json separateProfit 누계 = report 전체 누적 실현 순손익
[ ] 같은 날짜의 separateProfit 레코드가 중복되지 않음
[ ] 본 포지션 + 단타 매도수량 = 전체 매도수량
[ ] 본 포지션 + 단타 손익/비용/순손익 = 전체 합계
[ ] 본 포지션/단타 비중이 최신 순손익 기준으로 갱신됨
[ ] Chart 마지막 날짜·일별 순손익·누적값이 최신 표와 일치
[ ] Hero/KPI/전체결과/모바일카드의 숫자가 표 합계와 일치
[ ] 매도일 기준 승률 = 순손익 > 0인 매도일 수 / 전체 매도일 수이며 소수점 첫째 자리 표시와 보조문구가 일치
[ ] Hero가 본 포지션 추정 순손익 / 추정 단타 순손익 / 누적 실현 순손익 순서의 3개 구성을 유지
[ ] Timeline에 새 거래가 누락되지 않음
[ ] calc/report의 viewport media가 메인 기준(≥1101 / 761~1100 / ≤760) 경계만 사용하고 add 전용 특수 viewport가 없음
[ ] 웹/태블릿 Timeline 좌측 날짜가 줄바꿈 없이 한 줄로 표시됨
[ ] 모바일 Timeline의 모든 카드 상단에 날짜가 표시됨
[ ] report 메뉴/본문/KPI에 자금 흐름·차입금 상환 후 자기자금 계산이 다시 생기지 않음
[ ] 최신 증권사 원본 이미지와 업데이트 문구가 일치
[ ] add/calc.html report link가 report/kodex-leverage-report.html인지 확인
[ ] dated report filename이나 이전 canonical 경로 참조가 남아 있지 않음
[ ] 과거 마지막 날짜/과거 누계/과거 총수량 문자열이 잘못 잔존하지 않음
```

## 13. 수정하지 말아야 할 것

새 거래 반영을 이유로 다음을 임의 변경하지 않는다.

```text
메인 대시보드 CSS/JS 구조
calc 계산식
퇴직연금 데이터
가격 갱신 workflow
KRX 가격 데이터 구조
별도수익 재투입 한도
본 포지션/단타 기존 분류 기준
자금 흐름/차입금 상환 후 자기자금 패널을 사용하지 않는 현재 canonical 방향
```

다른 개선 아이디어가 보여도 사용자가 요청하지 않았다면 새 거래 반영과 섞지 않는다.

## 14. 최종 한 문장 운영 원칙

> **새 KODEX 레버리지 실현거래가 생기면 증권사 확정 순손익을 `data/portfolio.json`과 `add/report/kodex-leverage-report.html`에 함께 반영하고, 본 포지션/단타·차트·합계·원본근거·타임라인을 동일 기준으로 갱신하되, 신규 매매의 자금 출처나 대출이자 등 금융비용은 추적하지 않고 자금 흐름/최종 자기자금 섹션도 만들지 않으며 report 파일명은 날짜와 관계없이 고정한다.**
