# 투자 대시보드

삼성증권 증권계좌와 퇴직연금 계좌의 날짜별 성과를 복원·분석하는 정적 웹 대시보드입니다. 정적 화면은 **GitHub Pages**, 데이터 저장과 GitHub Actions 실행 요청은 **Google Apps Script 웹 앱**을 사용합니다.

> 기준: 2026-08-14 현재 구현

---

## 주요 기능

- 날짜별 증권계좌·퇴직연금 성과 복원
- `연금+계좌 성과`, 증권계좌, 퇴직연금 성과 비교
- **증권계좌 / 퇴직연금 탭 전환**: 기본은 증권계좌이며 목차의 하위 항목을 눌러도 필요한 탭을 자동으로 먼저 엽니다.
- 증권계좌 보유분, 계좌별 성과 요약, 투자원금 원천·검산, 장부결과 VS 실제보유 표시
- `장부결과 VS 실제보유`의 **고정 차액 불변조건**과 내부자금 이동 회귀 검증
- **별도수익 ON/OFF**에 따른 투자원금·손익·수익률 비교
- **라이트 / 다크 테마**: 라이트가 기본이며 선택한 테마는 브라우저에 저장됩니다. 화면에는 ☀️/🌙 아이콘만 표시합니다.
- 모바일 표/카드 보기 전환 및 스마트폰 가로모드 대응
- 퇴직연금 현금성자산·기업적립금·추가 매수 등록·삭제 및 작업 모음 일괄 처리
- KRX 현재가 최신/누락 반영 및 선택일 재갱신
- 누적수익률/KOSPI, 운용수익/수익률, 누적손익/손익률 등 차트 모드 전환
- 증권계좌 평가액 비중 `유형별 / 종목별` 전환
- 주요 6개 차트의 모바일 가로 확대 및 웹 전체화면 확대
- 확대 차트의 범례 선택 시 `전체 / Y축 자동 재계산 ON·OFF` 도구가 **floating toolbar**로 나타나 차트 높이를 줄이지 않습니다.
- 웹 우측 가장자리 목차, 모바일 햄버거 통합 메뉴, 웹·모바일 `TOP` 버튼
- 히어로의 `X월 X일 종가 기준` 문구를 빠르게 3회 클릭/탭하면 PIN 없이 개인보기로 진입합니다.
- 별도 투자 계산기(`calc.html`)와 거래 리포트(`report/`)

## 화면 조작

### 기준일 선택

상단의 년/월 셀렉트와 일·요일 셀렉트에서 조회 기준일을 선택합니다. 선택 가능한 날짜는 데이터 파일에 존재하는 날짜를 기준으로 생성됩니다. 웹·태블릿 상단에는 별도의 `기준일` 텍스트 라벨을 두지 않습니다.

모바일 기본 상태에서는 우측 상단에 **테마 아이콘 버튼과 햄버거 버튼**만 표시합니다. 햄버거 메뉴를 열거나 `날짜 선택 고정`을 켜면 상단이 다음 한 줄 구조로 바뀝니다.

```text
[년/월] [일] [☀️/🌙] [☰]
```

- 테마 버튼과 햄버거 버튼은 `.mobile-topbar-icon-btn` 공통 레이아웃을 사용합니다.
- 모바일 햄버거 메뉴 안에는 별도의 `화면`/테마 메뉴를 만들지 않습니다.
- 모바일의 년/월·일 셀렉트 폭은 테마/햄버거 버튼과 한 줄을 유지하도록 조정되어 있습니다.
- `날짜 선택 고정` 설정값은 브라우저에 저장됩니다.

### 목차

- 모바일: 상단 `☰` 버튼을 누르면 링크·관리·페이지 목차가 포함된 통합 메뉴가 열립니다.
- 웹·태블릿: 화면 맨 오른쪽 가장자리의 세로형 `목차` 탭에 마우스를 올리거나 키보드 포커스를 두면 목차 패널이 펼쳐집니다.
- 웹·태블릿 목차에는 페이지 내 이동 항목만 표시하며 링크와 관리 기능은 포함하지 않습니다.
- 과거 목차에 있던 개인보기 경고 아이콘과 `820421` PIN 진입 기능은 제거되었습니다. 관련 SVG·버튼·prompt/CSS를 다시 만들지 않습니다.

목차 항목을 선택하면 해당 영역으로 부드럽게 이동합니다. 증권계좌/퇴직연금 탭의 숨겨진 하위 항목을 선택한 경우에는 **대상 탭을 먼저 자동 전환한 뒤 이동**합니다.

### TOP 버튼

웹과 모바일에서 화면을 일정 거리 이상 내리면 우측 하단에 `TOP` 버튼이 나타납니다. 누르면 화면 최상단으로 이동합니다.

### 표 / 카드 보기

주요 데이터 영역은 모바일에서 표와 카드 보기를 전환할 수 있습니다. 기본값은 표이며, 스마트폰 가로모드에서 카드 보기를 선택한 경우 2열 카드 배치를 사용합니다.


### 증권계좌 / 퇴직연금 탭

자산 상세 영역은 `증권계좌`와 `퇴직연금` 탭으로 구분합니다.

- 최초 진입 기본 탭은 **증권계좌**입니다.
- 두 패널은 DOM을 삭제·재생성하지 않고 `hidden` 상태로 전환하므로 기존 section ID와 차트 구조를 유지합니다.
- 탭 전환 후 반응형 차트 컨트롤과 스크롤 힌트를 다시 동기화합니다.
- 목차의 하위 항목을 눌렀을 때 현재 숨겨진 탭에 속한다면 대상 탭을 먼저 열고 해당 section으로 이동합니다.
- 증권계좌 band는 Blue/Indigo 계열, 퇴직연금 band는 Emerald/Teal 계열의 **매우 약한 배경 gradient**를 사용합니다. 안쪽 카드마다 같은 gradient를 반복하지 않습니다.

### 라이트 / 다크 테마

- 기본은 라이트 테마입니다.
- 다크 테마 선택값은 `localStorage`의 `investmentDashboard.theme`에 저장합니다.
- `index.html`에서 초기 테마를 CSS 로드 전에 적용해 불필요한 흰 화면 flash를 줄입니다.
- 웹·태블릿과 모바일 모두 화면에는 `밝은 모드`, `다크 모드` 같은 텍스트를 표시하지 않고 **☀️/🌙 아이콘 버튼만** 사용합니다. 접근성을 위한 `title`, `aria-label`은 유지합니다.
- 모바일 테마 버튼은 햄버거 메뉴 내부가 아니라 **햄버거 버튼 바로 왼쪽**에 둡니다.
- 다크 테마는 `html.dark`에서 공통 색상 토큰을 바꾸는 방식이 기본입니다. 새 컴포넌트를 추가할 때 라이트/다크용 CSS를 각각 복제하지 않습니다.
- 양수/음수/차액의 의미색은 `--value-positive`, `--value-negative`, `--value-difference`를 사용합니다.
- 1주 보유 종목의 회색 표 배경처럼 테마에 따라 달라져야 하는 색은 `--soft-gray` 등 기존 토큰을 사용하고 라이트 전용 색상을 breakpoint 안에 하드코딩하지 않습니다.

### 개인보기

개인보기 진입은 히어로의 `X월 X일 종가 기준` 문구를 **700ms 이내 간격으로 3회 연속 클릭/탭**하는 숨은 제스처를 사용합니다. PIN 입력은 필요하지 않습니다.

- 웹 마우스와 모바일 탭 모두 동일한 `enterPersonalView()` 진입 경로를 사용합니다.
- 목차의 과거 경고 아이콘/PIN 진입 방식은 삭제된 기능이므로 복구하지 않습니다.
- KRX 실행 PIN과 퇴직연금 저장·삭제 PIN은 개인보기와 다른 관리 기능이므로 그대로 유지합니다.

## 별도수익 ON/OFF

별도수익 스위치는 6~8월 별도수익을 증권계좌 성과에 포함할지 선택하는 기능입니다.

### OFF

기본 장부 기준의 투자원금·누적손익·수익률을 표시합니다.

### ON

- 별도수익 누적액을 성과에 포함합니다.
- 별도수익 중 실제 재투자된 금액은 투자원금에서 제외해 **수익의 재투자를 신규 원금으로 중복 계산하지 않습니다.**
- 아직 현재 보유자산에 반영되지 않은 별도수익은 `장부결과 VS 실제보유`의 현금 보유액에 반영합니다.
- 따라서 장부상 결과물(A)과 실제 보유액(B)이 동일한 ON/OFF 기준을 사용하도록 맞춥니다.

`누적손익 및 누적수익률` 차트의 금액축은 ON/OFF를 비교할 때 축 자체가 변해 보이지 않도록 두 모드의 데이터 범위를 함께 반영합니다.

## 차트

### 비교 모드

퇴직연금의 `운용수익 및 누적수익률`, 증권계좌의 `누적손익 및 누적수익률` 차트는 `수익률 / 코스피` 버튼으로 우측 선 그래프를 전환합니다.

연금상품별 운용수익과 종목별 누적손익은 금액과 수익률 계열을 전환할 수 있습니다.

### 확대 보기

다음 6개 차트는 확대해서 볼 수 있습니다.

1. 퇴직연금 운용수익 및 누적수익률
2. 연금상품별 운용수익
3. 퇴직연금 평가액 비중
4. 증권계좌 누적손익 및 누적수익률
5. 종목별 누적손익
6. 증권계좌 평가액 비중

- 모바일 세로에서는 가로형 전체화면으로 확대합니다.
- 웹에서는 현재 브라우저 화면을 거의 가득 채우는 전체화면 형태로 확대합니다.
- 원본 차트의 스위치·범례·툴팁 상태를 확대 화면에서도 사용합니다.
- 범례 선택 후 나타나는 `전체 / Y축 자동 재계산 ON·OFF` 행은 확대창에서 **floating toolbar**로 배치하여 나타나거나 사라져도 차트 높이가 줄어들지 않게 합니다.
- 증권계좌 누적 차트의 웹 확대 화면에서도 별도수익 ON/OFF를 바로 전환할 수 있습니다.

## 평가액 비중

### 퇴직연금

- 상품은 **평가액이 높은 순**으로 차트·범례·카드를 표시합니다.
- 현금성자산은 차트 총평가액에 포함합니다.
- 상품 카드의 비중은 현금성자산을 제외한 상품 평가액 합계를 기준으로 계산합니다.
- `현재 평가총액`에는 현금성자산이 포함되며 하단에 포함 금액을 별도로 표시합니다.

### 증권계좌

`유형별 / 종목별` 스위치로 평가액 비중을 전환합니다.

#### 유형별

- ETF
- 개별주식
- 현금

#### 종목별

보유 종목을 평가액이 높은 순으로 표시합니다.

#### 1주 보유 종목과 현금 처리

- **정확히 1주 보유한 종목은 원칙적으로 평가액 비중 차트의 종목/유형 집계와 시각화 대상에서 제외합니다.**
- 단, 종목 데이터에 `chart: true`가 명시된 1주 종목은 **차트 표시 예외**로 허용합니다.
- 현재 예외 종목은 **삼성전기(`009150`) 1주**입니다. 삼성전기만 1주여도 차트에 표시하며, 다른 1주 종목의 기본 제외 규칙은 유지합니다.
- 하단 카드 등 1주 종목 제외 규칙은 차트 예외와 별개로 기존 화면 로직을 따릅니다. `chart: true`를 이유로 다른 UI까지 임의로 포함시키지 않습니다.
- 현금은 차트에는 포함하지만 하단 카드에서는 제외합니다.
- 하단 카드의 비중은 화면에 실제 표시되는 대상의 평가액 합계를 기준으로 계산합니다.
- `현재 평가총액` 자체에는 1주 종목과 현금을 모두 포함합니다.
- 포함 금액은 화면 로직에 따라 `(1주 종목 및 현금 ○○원 포함)` 형태로 표시할 수 있습니다.

1주 보유 여부와 `chart: true`는 **시각화 기준**일 뿐이며 종목의 ETF/개별주식 분류, 실제 보유수량·취득원가·평가총액 계산에는 영향을 주지 않습니다.

## 계좌별 성과 요약

계좌별 성과 요약에는 삼성증권1, 삼성증권2, 토스증권과 함께 통합 `합계`를 표시합니다.

삼성증권2의 일부 자금이 삼성증권1로 이동했기 때문에 **계좌별 투자원금을 단순 합산하지 않습니다.**

합계는 `연금+계좌 성과 > 증권계좌`의 기존 통합 계산값을 그대로 사용합니다.

- 투자원금 → 증권계좌 통합 투입원금
- 누적손익 → 증권계좌 통합 누적손익
- 수익률 → 증권계좌 통합 수익률

따라서 계좌 간 자금 이동으로 동일 원금이 중복 계산되는 것을 방지합니다.

## 투자원금 원천 및 검산

증권계좌 투자원금의 출처와 계좌1 투자원금 계산을 확인하는 영역입니다.

구성:

1. `계좌1 원천별 추적`
2. `전체 투입원금`
3. `계좌1 투자원금 검산`

계좌1 검산에서는 전체 투입원금에 재투입 수익과 기타 자금 흐름을 반영합니다. 별도수익 ON에서는 별도수익 재투입분을 신규 원금으로 다시 잡지 않도록 원금에서 재분류합니다.

### 원천 추적과 보유원가 정합

`계좌1 원천별 추적`은 실제 자금 원천 항목을 유지하면서, 선택일의 실제 보유종목 취득원가와의 차이를 `원천·보유 정합차액`으로 한 줄 추가해 최종 합계를 맞춥니다. 원천 이벤트 자체를 수정하거나 특정 날짜의 차액을 상수로 하드코딩하지 않습니다. `data/portfolio.json > constants.account1Principal`은 현재 원천 추적의 기준 앵커값으로 보존합니다.

2026-06-18 이후 장부 검산 구간에서는 내부적으로 다음 값을 날짜별로 계산합니다.

```text
원천 이벤트 추적 소계
= 기존 원천 이벤트를 선택일까지 역추적한 값

원천·보유 정합차액
= 선택일 보유종목 취득원가 합계
- 선택일 원천 이벤트 추적 소계

별도수익 OFF
계좌1 투자원금 합계
= 원천 이벤트 추적 소계 + 원천·보유 정합차액
= 선택일 보유종목 취득원가 합계

별도수익 ON
계좌1 투자원금 합계
= 원천 이벤트 추적 소계 + 원천·보유 정합차액
- 별도수익 재투입 원금 재분류액
```

`원천·보유 정합차액`은 **현금, 외부투입, 수익 또는 손실 항목이 아닙니다.** 원천별 역추적값과 실제 보유원가를 연결하는 날짜별 정합값이며, 양수·음수 모두 가능합니다.

화면에서는 다음 원칙을 사용합니다.

- 왼쪽 `계좌1 원천별 추적` 카드에 기존 원천 항목과 `원천·보유 정합차액`을 함께 표시합니다. 별도수익 ON이면 기존 재분류 규칙에 따라 `별도수익 재투입 원금 제외`도 함께 반영합니다.
- 왼쪽 카드의 최종 `합계`와 오른쪽 `계좌1 투자원금 검산`의 `계좌1 투자원금 합계`는 같은 값이어야 합니다.
- 오른쪽 검산 카드에서는 중복되는 `원천별 추적 합계`, `보유원가 기준 투자원금`을 별도 행으로 다시 표시하지 않습니다.
- `증권계좌 현금`과 `보유분+현금`은 원천·보유 정합차액과 다른 개념이므로 `계좌1 투자원금 검산`에서는 표시하지 않고 `증권계좌 보유분`에서 관리합니다.

현재 파일에서 확인되는 원천 이벤트 추적 소계와 보유원가 흐름은 다음과 같습니다.

| 기간 | 원천 이벤트 추적 소계 | 보유종목 취득원가 | 원천·보유 정합차액 | 증권계좌 현금 | 보유원가+현금 |
|---|---:|---:|---:|---:|---:|
| 2026-06-18 ~ 2026-08-07 | 16,283,348 | 16,282,745 | -603 | 17,255 | 16,300,000 |
| 2026-08-10 ~ 2026-08-11 | 22,983,348 | 22,996,210 | +12,862 | 3,790 | 23,000,000 |
| 2026-08-12 | 24,328,348 | 24,341,210 | +12,862 | 58,790 | 24,400,000 |

2026-08-10에는 별도수익 재투입 자금 유입이 총 6,700,000원이었고 KODEX AI반도체 실제 매수원금은 총 6,713,465원이었습니다. 차이 13,465원은 증권계좌 현금이 17,255원에서 3,790원으로 감소한 금액과 정확히 일치합니다. 이에 따라 원천·보유 정합차액도 -603원에서 +12,862원으로 13,465원 증가했습니다. 이 부분은 현재 JSON과 이벤트로 직접 확인됩니다.

2026-06-18 시점의 -603원은 당시 보유종목의 `feeBuffer` 합계 603원과 숫자가 정확히 일치합니다. 다만 현재 파일에는 이 603원을 특정 원천 이벤트나 수수료 자금 흐름으로 명시한 과거 기록이 없으므로, **수수료가 원인이라고 확정하지 않고 숫자상 강한 일치만 문서화**합니다.

2026-08-12의 `securitiesCash` 58,790원은 사용자가 직접 관리하는 현재 고정 현금값입니다. 8/11의 3,790원보다 55,000원 증가했지만 **원천·보유 정합차액 12,862원에는 영향을 주지 않습니다.** 따라서 현재 고정 현금 조정은 12,862원 차액의 원인으로 분류하지 않습니다.

별도수익 ON/OFF는 정합차액 계산 뒤에 적용합니다. 정합차액 자체는 모드와 무관하며, ON에서 합계가 줄어드는 것은 별도수익 재투입분을 성과기준 원금에서 제외하는 기존 재분류 규칙 때문입니다.

현재 원천 이벤트만으로 자금 출처별 역추적을 신뢰할 수 있는 기준은 `isLedgerCheckDate()`가 적용되는 **2026-06-18 이후**입니다. 그 이전 `account1_daily_snapshots.json`에는 보유원가·현금 데이터가 존재하지만 현재 `securitiesEvents`만으로 당시의 금 판매액·근로소득·회수 등 원천별 변동을 완전하게 복원할 수 없으므로, 6/18 이전 원천별 추적값을 새로 추정해 표시하지 않습니다.

### 자금 분류 원칙

증권계좌 자금 이벤트는 **돈이 계좌1에 들어왔다는 사실**과 **전체 투자자금이 새로 증가했는지 여부**를 구분해야 합니다.

- 일반 외부투입: 계좌1 원금과 전체 외부투입원금을 모두 증가시킬 수 있습니다.
- `performanceExcludedTransfer`: 이미 발생한 별도수익의 재투입입니다. 계좌1에는 들어오지만 별도수익 ON 원금에서는 신규 원금으로 중복 계산하지 않습니다.
- `internalCashTransfer`: 이미 보유 중이던 외부 현금을 증권계좌로 옮긴 **내부자금 이동**입니다. 계좌1 원천에는 표시할 수 있지만 전체 장부가치·전체 외부투입원금을 새로 증가시키면 안 됩니다.

**내부이동 금액을 일반 `contribution`과 동일하게 전체 장부결과에 더하면 장부결과(A)만 증가하여 `A-B` 불변조건이 깨집니다.** 내부이동을 추가·변경할 때는 계좌1 원금 복원과 전체 장부 중립 처리를 반드시 함께 확인합니다.

## 장부결과 VS 실제보유

증권계좌 장부상 결과와 실제 현재 보유자산·현금이 어떻게 연결되는지 확인하는 영역입니다.

### 장부상 증권계좌 투자 결과물(A)

`연금+계좌 성과 > 증권계좌 투자 결과물`과 동일한 값입니다.

```text
계좌1 성과 + 계좌2 실현분 + 토스 실현분
- 기존 현금의 증권계좌 내부이동분
```

`internalCashTransfer`는 계좌1에서는 원금 유입으로 보일 수 있지만 **통합 장부에서는 자산 위치만 바뀐 것**이므로 A에 신규 가치로 남겨 두지 않습니다.

### 현재 증권계좌 및 현금 보유액(B)

```text
증권계좌 평가총액
+ 실현수익 반영 현금 보유액
```

실현수익 반영 현금 보유액은 별도 각주로 산정 근거를 표시합니다. 별도수익 ON에서는 아직 현재 보유자산에 반영되지 않은 별도수익도 이 현금 기준에 포함합니다.

### 차액(A-B) — 반드시 유지할 불변조건

2026-06-18 이후 장부 검산이 적용되는 모든 날짜에서 다음 조건을 **항상** 유지해야 합니다.

```text
장부결과(A) - 실제보유(B)
= livingSpent
= 3,063,626원
```

이 3,063,626원은 `수익실현분 카드대금 사용`으로 이미 현재 보유액에서 제외된 금액입니다.

#### 절대 금지

- 화면의 차액을 `3,063,626`으로 직접 하드코딩해서 계산 오류를 숨기지 않습니다.
- 내부자금 이동을 외부 신규투입으로 분류하지 않습니다.
- 한쪽(A 또는 B)에만 자금 이동을 반영해 차액을 억지로 맞추지 않습니다.
- 현재 증권계좌 현금값을 바꿨다는 이유로 과거 스냅샷의 현금을 일괄 덮어쓰지 않습니다.

#### 별도수익 ON/OFF 불변조건

별도수익을 ON/OFF하면 A와 B의 구성금액은 달라질 수 있지만 **차액은 달라지면 안 됩니다.**

```text
OFF: A - B = 3,063,626원
ON : A - B = 3,063,626원
```

별도수익 ON에서는:

```text
누적 별도수익
- 실제 재투입된 별도수익
= 현 보유자산 미반영 별도수익
```

을 B의 현금 기준에 더합니다. 재투입분은 신규 원금으로 중복 계산하지 않습니다.

#### 2026-08-12 기준 자금 이동 사례

삼성전기 1주 매수원금 **1,345,000원 전액**은 별도수익에서 뺀 것이 아니라 **2026-06-18 확인 현금 2,035,097원에서 사용한 내부자금 이동**입니다.

```text
6/18 확인 현금           2,035,097원
- 삼성전기 매수 사용     1,345,000원
= 8/12 이후 잔액           690,097원
```

2026-08-12 누적 별도수익은 7,743,379원이며 실제 재투입된 별도수익은 6,700,000원이므로:

```text
별도수익 미반영분        1,043,379원
6/18 현금 잔액              690,097원
별도수익 ON 현금 기준     1,733,476원
```

이 됩니다. **1,345,000원은 외부 신규투입금이 아닙니다.**

### 증권계좌 고정 현금 `securitiesCash`

`data/portfolio.json > constants.securitiesCash`는 체결내역에서 자동 역산하는 현금이 아니라 **현재 증권계좌 기준원금을 맞추기 위해 사용자가 직접 관리하는 현재 고정값**입니다.

2026-08-12 현재:

```text
보유종목 취득원가 합계   24,341,210원
+ securitiesCash              58,790원
= 증권계좌 기준원금       24,400,000원
```

운영 원칙:

- `securitiesCash` 변경을 설명하기 위한 가상의 `cashAdjustment`·외부투입 이벤트를 만들지 않습니다.
- `securitiesCash`를 실제 체결대금으로 다시 산출해 사용자가 지정한 값을 임의로 바꾸지 않습니다.
- 저장된 과거 `performance_snapshots.json`, `account1_daily_snapshots.json`의 현금은 현재 고정값 변경 때문에 소급 수정하지 않습니다.
- 현재값과 과거 스냅샷을 함께 다룰 때 `securitiesCashForDate()`의 과거 스냅샷 우선 원칙을 깨지 않습니다.

### 장부 검산 변경 시 필수 회귀 테스트

증권계좌 매수·매도, 외부투입, 내부현금 이동, 별도수익 재투입, `securitiesCash` 변경 등 **자금 관련 로직을 수정한 경우 아래 검증을 생략하지 않습니다.**

1. 2026-06-18 이후 저장된 모든 장부 검산 날짜를 순회합니다.
2. 각 날짜를 별도수익 **OFF / ON 두 번** 계산합니다.
3. 모든 경우 `A - B === 3,063,626`인지 검증합니다.
4. 내부이동 전 날짜의 A/B 값이 과거 결과와 달라지지 않았는지 확인합니다.
5. 내부이동 발생일 이후 외부투입원금이 내부이동 금액만큼 잘못 증가하지 않았는지 확인합니다.
6. 현재 날짜뿐 아니라 다음 거래일을 가정한 mock 데이터에서도 차액이 유지되는지 확인합니다.
7. 화면 표시값만 보지 말고 `calc()` 결과, `renderLedgerCheck()`에서 사용하는 A/B, 날짜별 원금 복원값을 함께 대조합니다.

**자금 관련 수정의 완료 조건은 화면이 정상적으로 보이는 것이 아니라, 위 불변조건과 회귀 테스트를 모두 통과하는 것입니다.**

## 정규장 종료 후 NXT 매수의 당일 평가

정규장 종료 후 NXT에서 신규 매수한 종목은 같은 날짜의 KRX 종가를 매수 후 평가가격으로 사용하면 안 됩니다.

현재 구현은 매수 이벤트의 `valuationPrice` / `valuationSource`를 사용해 **해당 매수일 하루에만 평가가격을 덮어씁니다.** 다음 거래일부터는 다시 정상 시장가격 흐름을 사용합니다.

2026-08-12 삼성전기 사례:

```text
종목             삼성전기 (009150)
매수가            1,345,000원
8/12 NXT 종가     1,348,000원
8/12 평가손익          +3,000원
```

운영 원칙:

- NXT 당일 평가가격을 KRX 종가인 것처럼 저장하지 않습니다.
- `scripts/update_prices.py`를 재실행해도 해당 날짜의 명시적 `valuationPrice`가 KRX 종가로 덮어써지지 않아야 합니다.
- 다음 거래일부터는 당일 NXT 예외가격을 계속 들고 가지 않습니다.
- 보유종목의 `feeBuffer`는 별도 데이터로 유지하며, 현재 보유분 화면의 일반 평가손익은 기존 화면 로직대로 `평가액 - 취득원가`를 표시합니다.

## KRX 현재가 반영

상단 `KRX 현재가 반영` 버튼에서 PIN을 입력한 뒤 실행합니다.

### 최신/누락 반영

- 날짜를 전달하지 않고 Google Apps Script에 실행을 요청합니다.
- 서버가 최신·누락 데이터와 당일 종가 반영 상태를 판단합니다.
- 이미 당일 종가까지 반영되어 있으면 GitHub Actions 실행을 건너뛸 수 있습니다.

### 선택일 재갱신

- 현재 화면에서 선택한 기준일을 전달합니다.
- 해당 날짜의 KRX 가격과 스냅샷을 다시 계산할 때 사용합니다.

### 실행 흐름

```text
대시보드
  → Google Apps Script 웹 앱
  → GitHub Actions workflow_dispatch
  → scripts/update_prices.py
  → data/prices.json / data/performance_snapshots.json 갱신
  → GitHub Pages 재배포
```

## 퇴직연금 금액 조정

상단 `퇴직연금 금액 조정`에서 다음 세 항목을 관리합니다.

### 현금성자산

- 기본 선택 항목입니다.
- 퇴직연금 앱에 표시된 특정일의 현금성자산 **평가금액과 매수원금**을 함께 저장합니다.
- 같은 날짜는 한 건만 유지하며 다시 저장하면 기존 항목을 수정합니다.

### 기업적립금

- 회사가 납입한 퇴직연금 적립금을 등록합니다.
- 같은 날짜에 여러 건이 있을 수 있어 `id` 기준으로 개별 관리합니다.

### 추가 매수

- 퇴직연금 앱에서 매수 신청한 ETF를 앱 반영일 기준으로 등록합니다.
- 화면에는 `신청일`로 표시하되 기존 데이터 호환을 위해 내부 필드명 `tradeDate`는 유지합니다.
- 체결수량과 체결금액을 기준으로 보유수량·원가·현금성자산을 반영합니다.

### 개별 처리 / 작업 모음

- `개별 처리`: 한 건씩 저장·삭제합니다.
- `작업 모음`: 여러 저장·삭제 작업을 임시로 모은 뒤 PIN 한 번으로 한 커밋에 일괄 반영합니다.
- 작업 모음에 추가하는 시점에는 서버 저장 완료 토스트를 표시하지 않고, 실제 서버 반영 성공 후 결과를 알립니다.

### PIN 및 저장

- Google Apps Script를 통해 GitHub JSON 파일에 직접 반영합니다.
- PIN은 **6자리**입니다.
- PIN 6자리가 일치하면 별도의 실행 버튼 없이 저장 또는 삭제를 진행합니다.
- PIN 오류는 PIN 입력 모달 안에 표시됩니다.

## 현금성자산 계산 기준

### 매수원금

`costBasis`가 저장된 현금성자산 스냅샷이 있으면 가장 최근 스냅샷의 매수원금을 기준점으로 사용하고, 이후 기업적립금·추가 매수 흐름을 반영합니다. 과거 스냅샷에 `costBasis`가 없으면 기존 계산 기준을 유지합니다.

- 기업적립금은 매수원금과 평가금액에 함께 더합니다.
- 추가 매수는 평가금액에서 체결금액 전액을 차감합니다.
- 매수원금은 현금성자산의 평가이익을 먼저 사용한 뒤 부족한 금액만 차감합니다.
- 따라서 평가이익이 있는 경우 `체결금액 = 매수원금 감소액`이 아닐 수 있습니다.

### 평가금액

스냅샷이 없으면:

```text
기준 현금성자산 원금 + 해당일까지 등록된 기업적립금 누적액
```

스냅샷이 있으면:

```text
최근 현금성자산 평가금액 스냅샷
+ 스냅샷 이후 추가 기업적립금
- 이후 추가 매수 금액
```

### 평가손익

```text
현금성자산 평가금액 - 현금성자산 매수원금
```

## Google Apps Script 설정

Google Apps Script 웹 앱에는 다음 Script Properties가 필요합니다.

```text
ADMIN_PIN
GITHUB_TOKEN
GITHUB_OWNER
GITHUB_REPO
GITHUB_BRANCH
```

권장 Fine-grained GitHub Token 권한:

```text
Repository access: 투자 대시보드 저장소만 선택
Contents: Read and write
Actions: Read and write
Metadata: Read-only
```

용도:

- `Contents: Read and write`: 퇴직연금 JSON 저장·삭제
- `Actions: Read and write`: KRX 업데이트 워크플로 실행
- `Metadata: Read-only`: 저장소 기본 접근

Apps Script 코드를 바꾼 경우에는 새 버전으로 웹 앱을 다시 배포합니다. Script Properties 값만 변경한 경우에는 일반적으로 코드 재배포가 필요하지 않습니다.

## 프론트엔드 / CSS 유지보수 원칙

이 프로젝트의 CSS는 여러 차례의 UI 개선 후 **공통 컴포넌트·디자인 토큰 중심으로 리팩토링된 상태**입니다. 이후 종목·상품·카드·모달·차트 기능을 추가할 때는 화면만 맞추는 것보다 **기존 공통 CSS를 재사용하고 CSS 찌꺼기를 만들지 않는 것**을 우선합니다.

### 기본 원칙

1. **파일 맨 아래에 임시 override를 덧붙여 해결하지 않습니다.**
   - 기존 최종 rule과 해당 breakpoint를 먼저 찾습니다.
   - 새 동작이 기존 공통 규칙으로 표현 가능하면 원래 선언을 직접 수정합니다.
   - 기존 선언이 완전히 대체되면 사문화된 rule·주석·`!important`도 함께 제거합니다.

2. **공통 컴포넌트를 우선 재사용합니다.**
   - 메인 섹션 제목·좌측 아이콘·우측 기준/보기 칩
   - `.mobile-data-card` 기반 모바일 카드 보기
   - `.mini-card`, `.metric-card`
   - `.asset-color-swatch`
   - 차트 스위치·범례·확대·좌우 이동·`전체`·Y축 자동재계산 control
   - 공통 tooltip surface
   - 웹 우측 목차 / 모바일 햄버거 메뉴 primitive
   - KRX/퇴직연금 모달의 공통 modal shell·카드·segmented control
   - KPI/미니카드를 제외한 큰 surface(`.note`, `.chart-card`, `.pension-band`, `.securities-band`)

3. **색상·크기·상태는 기존 디자인 토큰을 먼저 확인합니다.**
   - 기본 surface/text/border: `--bg`, `--card`, `--ink`, `--muted`, `--line`
   - 양수/음수/차액: `--value-positive`, `--value-negative`, `--value-difference`
   - 테마 대응 회색: `--soft-gray`
   - 차트: `--chart-surface`, `--chart-grid`, `--chart-axis`, `--chart-text` 등
   - 차트 control: `--dashboard-control-*`
   - tooltip: `--tooltip-*`
   - 증권/연금 band: `--securities-band-bg`, `--pension-band-bg`

4. **다크모드는 토큰 우선입니다.**
   - 새 요소가 단순 surface/text/border 차이라면 `html.dark`용 개별 selector를 추가하기 전에 기존 토큰만으로 해결 가능한지 확인합니다.
   - 기능상 별도 active/hover 상태가 필요한 경우에만 해당 컴포넌트 가까이에 dark modifier를 둡니다.
   - 라이트 전용 hex 색상을 모바일/태블릿 breakpoint 안에 다시 하드코딩하지 않습니다.

5. **`!important`는 새로 늘리지 않는 것을 기본으로 합니다.**
   - 기존 cascade·Safari/native control·sticky table 등 실제 이유가 있는 경우만 유지합니다.
   - specificity를 덮기 위해 `!important`를 추가하기 전에 selector 구조와 기존 rule을 정리합니다.

6. **기능 삭제 시 DOM/JS/CSS를 함께 제거합니다.**
   - 예: 과거 목차 개인보기 경고 아이콘처럼 기능이 삭제되면 생성 함수, event, SVG, 전용 selector까지 잔여가 없게 정리합니다.

### 반응형 기준

기본 breakpoint는 다음을 기준으로 유지합니다.

```text
웹      : 1101px 이상
태블릿  : 761px ~ 1100px
모바일  : 760px 이하
```

추가 breakpoint는 **실제 기능상 이유가 있을 때만** 사용합니다.

- `900px`: iPad Mini/compact tablet 및 모바일 가로처럼 실제 레이아웃 차이가 필요한 구간
- `374px`: 아주 좁은 스마트폰에서 상단 날짜·아이콘 control의 최소 폭/폰트를 보존하는 예외
- iPhone Safari 날짜 input, input zoom, 실제 desktop-site 요청 등 브라우저 동작 대응 규칙은 단순 CSS 찌꺼기로 보지 않습니다.

새 UI를 추가할 때 임의로 `520px`, `430px` 같은 breakpoint를 먼저 만들지 말고, **기존 1101/761/760 체계로 해결 가능한지 먼저 확인**합니다.

### 신규 종목·상품 추가/변경 시 CSS 원칙

새 종목을 매수하거나 기존 보유종목의 수량·유형·차트 표시 여부가 바뀌었을 때 **종목별 전용 CSS를 새로 만드는 것을 기본 해법으로 사용하지 않습니다.**

1. 우선 `data/portfolio.json`, 가격/스냅샷, 거래 이벤트 등 **데이터와 계산 로직**을 수정합니다.
2. 종목명·상품명 우측 `■`의 **모양·크기·정렬은 `.asset-color-swatch` 공통 CSS**를 그대로 사용합니다.
3. 종목/상품 색상은 CSS class가 아니라 `script.js`의 공통 색상 원천을 사용합니다.
   - 증권 종목: `SECURITY_SYMBOL_COLORS`
   - 퇴직연금 상품: `PENSION_PRODUCT_COLORS`
   - 유형: `ASSET_TYPE_COLORS`
   - 고정 색상이 없는 신규 증권 종목은 `securityAllocationColor()`의 fallback 체계를 우선 사용합니다.
4. 특정 종목의 이름 색상·카드 배경을 맞추기 위해 `.ticker-새종목` 같은 전용 색상 CSS를 만들지 않습니다.
5. `cssClass`가 필요한 경우에도 **기존 공유 의미**(예: 1주 표 표시)로만 사용하며, 디자인을 개별 종목에 종속시키지 않습니다.
6. 1주 종목의 회색 처리는 **증권계좌 보유분의 표 보기**에만 적용합니다. 모바일 카드 전체 배경으로 번지게 만들지 않습니다.
7. 1주 종목의 차트 포함 여부는 `chart`, 필요 시 `chartFrom` 데이터로 제어합니다. `chart: true`를 이유로 다른 UI 규칙까지 임의 변경하지 않습니다.
8. 정규장 종료 후 NXT 매수처럼 특정일 평가 예외가 필요하면 CSS가 아니라 기존 `valuationPrice` / `valuationSource` 흐름을 사용합니다.
9. 신규 종목 추가 후에는 최소한 다음 표시를 함께 확인합니다.
   - 증권계좌 보유분 표/모바일 카드
   - 종목별 누적손익과 범례/`■`
   - 평가액 비중 유형별/종목별
   - 1주 제외/예외 규칙
   - 라이트/다크 테마
   - 900px 이하 sticky 종목명 셀 배경

### 미니카드 그리드 구조 변경 규칙 — 임의 변경 금지

미니카드는 같은 `.mini-card` surface를 공유하지만 **섹션마다 한 줄 카드 수와 span 규칙이 의도적으로 다릅니다.** 신규 카드가 생겼다는 이유로 전체를 같은 열 수로 통일하면 안 됩니다.

현재 대표 구조:

- 누적 성과 6개 요약카드 `.chart-note.six`
  - 웹: 6열
  - 태블릿: 3열
  - 모바일 세로: 2열
  - 스마트폰 가로: 3열
- 상품/종목별 성과 `.chart-note.symbol-summary-grid`
  - 웹/태블릿은 높은 정보밀도를 유지
  - 모바일 세로는 2열
  - iPad Mini 구간은 기존 4열 밀도를 유지하도록 별도 의도가 있습니다.
- 퇴직연금 평가액 비중
  - 웹/태블릿: 4열
  - 모바일: 2열
- 증권계좌 평가액 비중
  - `유형별 / 종목별`에 따라 카드 수가 다릅니다.
  - `현재 평가총액` 카드는 화면/모드에 따라 **2칸을 차지하거나 한 줄 전체를 차지하는 구조**가 있습니다.

따라서 **신규 미니카드 추가, 삭제, 한 줄 카드 수 변경, `grid-column` span 변경이 필요할 때는 바로 코드를 바꾸지 않습니다.** 먼저 사용자에게 다음을 확인합니다.

1. 어느 viewport에서 몇 장을 한 줄에 둘지
2. 총액/합계 카드가 1칸, 2칸 또는 한 줄 전체 중 무엇이 맞는지
3. 새 카드가 기존 카드와 같은 우선순위인지, 별도 강조가 필요한지
4. 웹/태블릿/모바일/모바일 가로에서 구조를 동일하게 할지 다르게 할지

그 다음 **현재 구조를 설명하고 2~3개의 배치 대안을 제안한 뒤 사용자 선택을 받아** 기존 공통 grid rule 또는 modifier 안에서 정리합니다. 이 과정 없이 카드 수를 보고 임의로 `repeat(N, ...)`, 새 breakpoint 또는 새 span CSS를 만들지 않습니다.

### CSS 수정 후 최소 검증 및 보고

단순 CSS 수정·공통화·찌꺼기 제거는 과도한 전체 회귀테스트보다 다음 경량 검증을 기본으로 합니다.

1. 수정 대상의 기존 selector / breakpoint / dark rule을 먼저 확인
2. 새 후행 override를 만들지 않았는지 확인
3. CSS 문법과 중괄호 검사
4. 수정 대상 selector의 불필요한 중복/사문화 rule 검사
5. `diff`로 의도한 파일과 선언만 바뀌었는지 확인
6. `style.css` 수정 전/후 **전체 줄 수·증감 줄 수** 보고
7. `style.css` 수정 전/후 **파일 크기(bytes)·증감 크기** 보고
8. 변경 파일별 diff 추가/삭제 줄 수와 예상 밖 변경 여부 보고

다만 `display`, `position`, `grid`, `flex`, `width/height`, fixed/sticky/overlay, breakpoint, DOM class 또는 JS 렌더링을 바꾼 경우에는 해당 대표 viewport에서 필요한 렌더 확인을 추가합니다.

### 변경 범위 원칙

- 최신 운영 파일을 기준으로 **필요한 파일만 최소 수정**합니다.
- CSS 공통화 때문에 계산·데이터 로직을 함께 바꾸지 않습니다.
- 새로운 기능을 넣을 때 기존 공통 CSS로 해결할 수 있으면 새 selector보다 공통 class/modifier를 우선합니다.
- 기존 UI가 특수한 이유가 있는지 확인하지 않고 “더 깔끔해 보인다”는 이유만으로 열 수·span·breakpoint를 통일하지 않습니다.
- 한 기능을 고친 뒤 다른 화면의 최종 디자인이 롤백되지 않도록, 해당 공통 class를 사용하는 영역의 영향 범위를 diff로 확인합니다.

## 운영 데이터 주의

다음 파일은 실제 운영 데이터이므로 소스 ZIP을 GitHub에 반영할 때 **커밋 전에 GitHub의 현재 운영본과 반드시 비교**합니다.

```text
data/portfolio.json
data/prices.json
data/performance_snapshots.json
data/account1_daily_snapshots.json
data/pension_contributions.json
data/pension_cash_snapshots.json
data/pension_trades.json
```

- `portfolio.json`은 보유종목뿐 아니라 증권계좌 현금·원금·장부 검산 기준과 자금 이벤트를 포함하므로 **현재 운영본을 최우선으로 확인**합니다.
- `prices.json`, `performance_snapshots.json`은 워크플로 실행으로 복구·재생성할 수 있는 범위가 있습니다.
- `account1_daily_snapshots.json`은 과거 증권계좌 현금·평가액 복원에 사용되므로 현재 `securitiesCash` 변경을 이유로 소급 덮어쓰지 않습니다.
- `pension_contributions.json`, `pension_cash_snapshots.json`, `pension_trades.json`은 화면에서 직접 등록한 운영 이력이므로 소스 ZIP의 과거 파일로 덮어쓰지 않도록 특히 주의합니다.
